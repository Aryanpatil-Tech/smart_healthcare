# Smart Digital Healthcare & Patient Medical Record Management System

A server-rendered Django starter for patient-owned health records with role-based access, explicit time-limited consent, private documents, and QR identity tokens. This is a development foundation using synthetic data only—not a clinically or regulatorily approved product.

## Project structure

```text
smart_healthcare/
├── accounts/          Custom user model, registration and role-based authentication
├── patients/          Patient demographic and emergency profile
├── doctors/           Doctor credentials and verification
├── hospitals/         Hospital approval and staff accounts
├── medical_records/   Diseases, treatments, prescriptions, reports and appointments
├── health_cards/      Random QR lookup token and printable digital card
├── consent/           Consent requests and immutable access audit trail
├── dashboard/         Public pages, role dashboards and admin overview
├── config/            Django settings, root URLs and WSGI entry point
├── templates/         Shared and feature templates
└── static/css/        Responsive, no-JavaScript stylesheet
```

## Initial normalized SQL schema

Django models create the relational SQL schema (SQLite by default; MySQL configuration documented below). Primary keys are generated by Django; foreign keys are indexed by default. Unique constraints protect usernames, email, patient IDs, QR tokens, medical registration numbers and consent scope relationships.

- **Users**: authentication identity, unique username/email, role (`PATIENT`, `DOCTOR`, `HOSPITAL`, `STAFF`, `ADMIN`). Passwords are Django-hashed.
- **Patients**: one-to-one user, unique patient ID and cryptographically random lookup token, demographic, address and emergency fields.
- **Hospitals**: account, address/contact data and approval status. **HospitalStaff** links staff users to a hospital and active status.
- **Doctors**: one-to-one user, qualification, specialty, registration number, experience, optional hospital and verification status.
- **Diseases**: normalized disease catalog with a unique name.
- **Treatments**: patient, doctor, hospital, disease, symptoms, diagnosis, treatment, status and dates. Patient/date index supports timelines.
- **Prescriptions**: treatment-level prescription; **PrescriptionMedicines** holds medicine, dosage and duration in normalized rows.
- **MedicalReports**: treatment, private file path, metadata, report type and upload time. Files are served only through an authorization-checked view.
- **Appointments**: patient, doctor, hospital, treatment link, date, follow-up notes and status.
- **ConsentRequests**: patient, requesting account, independent history/prescription/report scopes, pending/approved/rejected/revoked status, expiry and timestamps.
- **AccessLogs**: patient, actor, action and timestamp; ordered and indexed for audit review.

## Implementation plan

1. Establish custom account roles and registration/login with Django CSRF and password hashing.
2. Add profile models, verification workflows and role-protected dashboards.
3. Add normalized treatment, prescription, report and appointment records.
4. Add patient-controlled, scoped, expiring consent; log requests, approvals, views and downloads.
5. Issue private QR tokens that resolve to an identity-verification page only; no medical data is encoded.
6. Add report download authorization and printable health cards.
7. Complete server-rendered responsive pages, synthetic seed command, setup instructions and validation.

## Local development

Use Python 3.11+ recommended. From this directory:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py makemigrations accounts patients doctors hospitals medical_records consent
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Open `http://127.0.0.1:8000/`. Admin verification is available at `/admin/`. Run `python manage.py seed_demo` to create synthetic example profiles and records; it never creates real patient information. The demo credentials are printed by the command and must not be used outside local development.

To scan the health card from a phone on the same Wi-Fi, find the computer's LAN IPv4 address with `ipconfig`, set `DJANGO_ALLOWED_HOSTS` to include that address, and start Django with `python manage.py runserver 0.0.0.0:8000`. Open the site on the computer using `http://<computer-LAN-IP>:8000/` before displaying the card so its QR code uses a phone-reachable address. Keep this development server on a trusted local network; do not expose it to the public internet.

### MySQL option

Install a MySQL server and `mysqlclient`, create a database and least-privilege application user, then set `DB_ENGINE=django.db.backends.mysql`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, and `DB_PORT` in the environment. Never commit production credentials. Apply migrations after configuring the environment.

## Security and production notes

- Configure HTTPS, secure cookies, a secret key from a secrets manager, `DEBUG=False`, restrictive `ALLOWED_HOSTS`, database backups/encryption, retention policies, malware scanning and operational monitoring before deployment.
- Files are stored under `private_uploads/`, which is not mapped to a public URL. Use the authenticated report endpoint only.
- Consent is purpose-scoped and expires; QR lookup is not authorization. Doctors/hospital staff must be verified/approved to request access.
- The starter cannot replace independent threat modeling, penetration testing, privacy review, accessibility review, clinical safety validation or jurisdiction-specific regulatory/legal assessment. Do not use for real clinical care.
